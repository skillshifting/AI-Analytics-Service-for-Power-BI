# AI Analytics Service for Power BI

Прототип AI-сервиса, который преобразует вопросы пользователя на естественном языке в безопасные SQL-запросы, выполняет их над локальным датасетом и сохраняет результат для последующего использования в Power BI.

## О проекте

Сервис позволяет пользователю задать аналитический вопрос обычным языком, например:

```text
Покажи общую сумму заказов по регионам
```

После этого система:

1. загружает CSV-файлы в DuckDB;
2. извлекает структуру таблиц и колонок;
3. формирует контекст для языковой модели;
4. отправляет вопрос и метаданные в OpenRouter;
5. получает SQL, пояснение, DAX и рекомендации по визуализации;
6. проверяет SQL перед выполнением;
7. выполняет безопасный запрос в DuckDB;
8. сохраняет результат в CSV для Power BI;
9. сохраняет технический анализ в JSON.

Ключевой принцип решения:

> LLM не получает полный датасет и не выполняет SQL самостоятельно. Модель только предлагает запрос, а программный код проверяет и выполняет его в контролируемой среде.

## Основные возможности

- преобразование естественного языка в SQL;
- автоматическое извлечение метаданных;
- работа с несколькими связанными таблицами;
- генерация SQL в диалекте DuckDB;
- генерация рекомендаций по DAX;
- рекомендации по визуализациям Power BI;
- проверка SQL через SQLGlot;
- запрет операций изменения данных;
- ограничение доступа белым списком таблиц;
- проверки качества исходного датасета;
- сохранение результата в CSV;
- сохранение полного ответа модели в JSON;
- возможность заменить OpenRouter на Azure OpenAI;
- возможность заменить DuckDB на корпоративную СУБД.

## Преимущества решения

### 1. Модель не получает все строки датасета

В LLM передаются преимущественно:

- названия таблиц;
- названия колонок;
- типы данных;
- результаты проверок качества;
- вопрос пользователя.

Это уменьшает:

- объём передаваемых данных;
- стоимость запросов к модели;
- риск раскрытия чувствительной информации;
- вероятность превышения контекстного окна.

### 2. LLM отделена от выполнения SQL

Модель генерирует предложение, но не имеет прямого подключения к базе.

SQL проходит следующий путь:

```text
LLM
 ↓
Программная валидация
 ↓
DuckDB
```

Такой подход позволяет контролировать действия модели.

### 3. Используется детерминированный контур безопасности

Системный промпт просит модель создавать только `SELECT`, но промпт не считается полноценной защитой.

Дополнительно код:

- запрещает опасные команды;
- проверяет количество SQL-выражений;
- разбирает SQL в синтаксическое дерево;
- проверяет используемые таблицы;
- отклоняет некорректные запросы до обращения к базе.

### 4. Модульная архитектура

Каждый файл отвечает за отдельную область:

- база данных;
- метаданные;
- промпты;
- работа с моделью;
- валидация;
- оркестрация.

Это упрощает тестирование, сопровождение и замену компонентов.

### 5. Простое подключение к Power BI

Результат аналитического запроса сохраняется в:

```text
outputs/result.csv
```

Файл можно импортировать в Power BI без разработки отдельного API.

### 6. Быстрая замена инфраструктуры

В MVP используется:

```text
CSV + DuckDB + OpenRouter
```

В корпоративной версии компоненты можно заменить:

```text
SQL Server / Oracle / Snowflake / Fabric
Azure OpenAI
Power BI Semantic Model
REST API или внутренний сервис
```

Основная логика оркестрации при этом сохраняется.

### 7. Поддержка аудита

В `analysis.json` сохраняются:

- объяснение модели;
- использованные таблицы;
- предупреждения;
- сгенерированный SQL;
- DAX;
- рекомендации по визуализациям.

Это позволяет анализировать и отлаживать поведение LLM.

## Как проходит запрос

### Шаг 1. Загрузка данных

CSV-файлы из папки `data` загружаются в DuckDB.

```text
crm_users_raw.csv  -> crm_users_raw
orders_hub.csv     -> orders_hub
geo_dictionary.csv -> geo_dictionary
```

### Шаг 2. Извлечение метаданных

Сервис обращается к `information_schema.columns` и получает описание таблиц:

```json
{
  "table_name": "orders_hub",
  "column_name": "total_amt",
  "data_type": "DOUBLE"
}
```

### Шаг 3. Проверка качества

Сервис может проверять:

- дубликаты идентификаторов клиентов;
- дубликаты географических кодов;
- пропущенные email;
- заказы без соответствующего пользователя;
- заказы с неизвестным географическим кодом.

### Шаг 4. Формирование промпта

Модель получает:

- правила генерации;
- вопрос пользователя;
- схему базы;
- результаты проверок качества.

### Шаг 5. Генерация ответа

LLM возвращает структурированный JSON:

```json
{
  "explanation": "Описание логики запроса",
  "tables_used": ["orders_hub", "geo_dictionary"],
  "warnings": [],
  "sql": "SELECT ...",
  "dax_measures": [],
  "recommended_visuals": []
}
```

### Шаг 6. Валидация SQL

До выполнения проверяется:

- запрос не пустой;
- используется только одно SQL-выражение;
- отсутствуют запрещённые команды;
- запрос является аналитическим;
- используются только разрешённые таблицы.

### Шаг 7. Выполнение

Проверенный SQL выполняется в DuckDB.

### Шаг 8. Сохранение

Создаются:

```text
outputs/result.csv
outputs/analysis.json
```

## Описание файлов

### `main.py`

Точка входа и оркестратор приложения.

Отвечает за последовательность:

```text
инициализация базы
-> сбор метаданных
-> получение вопроса
-> вызов модели
-> проверка SQL
-> выполнение SQL
-> сохранение результата
```

### `database.py`

Слой доступа к данным.

Основные задачи:

- создание подключения к DuckDB;
- загрузка CSV в таблицы;
- выполнение SQL;
- возврат результата как Pandas DataFrame;
- гарантированное закрытие соединения.

### `metadata.py`

Формирует контекст для модели.

Основные задачи:

- извлечение таблиц и колонок;
- получение типов данных;
- проверки качества;
- очистка некорректных Unicode-символов;
- преобразование метаданных в JSON.

### `prompts.py`

Содержит системную инструкцию для LLM.

Промпт задаёт:

- роль аналитического ассистента;
- диалект SQL;
- формат JSON;
- требование использовать только существующие поля;
- требование формировать только безопасные аналитические запросы;
- правила формирования DAX и рекомендаций по визуализации.

### `llm.py`

Адаптер для работы с OpenRouter.

Основные задачи:

- загрузка API-ключа и модели из `.env`;
- создание OpenAI-совместимого клиента;
- формирование сообщения модели;
- ограничение максимального размера ответа;
- получение ответа;
- очистка Markdown-обёртки;
- разбор JSON;
- проверка обязательных полей ответа.

### `validator.py`

Защитный слой между моделью и базой.

Основные задачи:

- поиск запрещённых SQL-команд;
- разбор SQL через SQLGlot;
- запрет нескольких выражений;
- проверка типа запроса;
- извлечение используемых таблиц;
- проверка таблиц по белому списку.

### `requirements.txt`

Список зависимостей:

```text
duckdb
pandas
openai
python-dotenv
sqlglot
```

Рекомендуется фиксировать версии библиотек после стабилизации проекта.

### `.env`

Содержит секреты и настройки:

```env
OPENROUTER_API_KEY=sk-or-v1-...
OPENROUTER_MODEL=имя-модели
```

Файл нельзя загружать в публичный репозиторий.

### `.gitignore`

Исключает из Git:

- `.env`;
- виртуальное окружение;
- Python cache;
- локальную DuckDB;
- временные результаты;
- системные файлы IDE и macOS.

### `data/`

Исходные CSV-файлы.

В промышленной версии вместо них может использоваться внешняя СУБД или Lakehouse.

### `outputs/`

Результаты работы приложения:

- `result.csv` — данные для Power BI;
- `analysis.json` — технический ответ модели.

В вызове модели рекомендуется явно ограничивать ответ:

```python

    model=model,
```

## Безопасность

### Белый список таблиц

Разрешены только заранее определённые таблицы:

```python
ALLOWED_TABLES = {
    "crm_users_raw",
    "orders_hub",
    "geo_dictionary",
}
```

### Запрещённые операции

Сервис блокирует команды, которые могут изменять данные или структуру базы:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
CREATE
TRUNCATE
COPY
ATTACH
DETACH
```

### Только один SQL-запрос

Конструкция вида:

```sql
SELECT * FROM orders_hub;
DROP TABLE orders_hub;
```

должна быть отклонена, поскольку содержит несколько выражений.

### Парсинг, а не только поиск строк

SQLGlot используется для построения синтаксического дерева SQL. Это надёжнее, чем проверка только через строковый поиск.

### Минимальные права базы

В промышленной системе подключение должно использовать read-only пользователя, даже если программная валидация уже реализована.

### Защита секретов

API-ключ хранится в `.env`, а сам файл добавляется в `.gitignore`.

Никогда не публикуйте реальный API-ключ в GitHub.

## Обработка качества данных

До формирования SQL сервис может обнаруживать проблемы, способные исказить результат.

### Дубликаты ключей

Дубликат клиента или географического кода может привести к размножению строк после `JOIN`.

### Orphan records

Заказ может ссылаться на пользователя, которого нет в справочнике.

### Неизвестные географические коды

Заказ может содержать `geo_code`, которого нет в `geo_dictionary`.

### Пропущенные значения

Отсутствующие email, суммы, даты или ключи могут влиять на аналитику.

### Unicode и кодировка

Перед отправкой текста модели выполняется очистка некорректных Unicode-surrogate символов.

Исходные CSV желательно хранить в UTF-8.

## Пример запроса

Вопрос:

```text
Покажи общую сумму заказов по регионам
```

Возможный SQL:

```sql
SELECT
    g.region_name,
    SUM(o.total_amt) AS total_amount
FROM orders_hub AS o
JOIN geo_dictionary AS g
    ON o.geo_code = g.geo_code
GROUP BY
    g.region_name
ORDER BY
    total_amount DESC
```

Перед выполнением сервис проверяет:

- используются ли реальные таблицы;
- отсутствуют ли опасные команды;
- является ли запрос одним выражением;
- разрешено ли выполнение такого типа запроса.

## Ограничения MVP

### Нет полноценного семантического слоя

Модель знает названия таблиц и колонок, но может не знать бизнес-определения.

Например:

```text
Revenue = только оплаченные и не отменённые заказы
```

Такие определения следует хранить в отдельном бизнес-глоссарии.

### CSV загружаются при запуске

Для демонстрационного решения это удобно, но в production данные обычно уже находятся в корпоративной базе.

### Нет API

Текущая версия работает как CLI-приложение.

Это осознанное упрощение MVP. Следующим этапом может стать FastAPI или другой внутренний API.

### Нет авторизации пользователей

В промышленной реализации необходимы:

- аутентификация;
- роли;
- row-level security;
- журналирование;
- ограничение доступных источников.

### LLM может ошибаться

Модель может вернуть:

- неправильный JSON;
- несуществующую колонку;
- синтаксически корректный, но бизнес-некорректный SQL.

Поэтому обязательны:

- программная валидация;
- тестовые запросы;
- семантический слой;
- мониторинг;
- аудит.

### CSV является промежуточным интерфейсом

Это удобно для демонстрации, но не является наиболее масштабируемым способом интеграции.

## Как представить проект на собеседовании

Краткое описание:

> Я разработал MVP AI-аналитического сервиса на Python. CSV-файлы загружаются в DuckDB, после чего система извлекает метаданные и проверки качества. Пользователь задаёт вопрос на естественном языке, а OpenRouter-совместимая LLM генерирует структурированный ответ с SQL, DAX и рекомендациями для Power BI. SQL не выполняется напрямую: сначала он проверяется через SQLGlot, ограничивается белым списком таблиц и набором разрешённых операций. После проверки запрос выполняется в DuckDB, а результат сохраняется в CSV для загрузки в Power BI.

Главная архитектурная мысль:

> LLM является недетерминированным компонентом внутри детерминированного контура безопасности.

Главная ценность решения:

> Сервис уменьшает путь от бизнес-вопроса до аналитического результата, но сохраняет программный контроль над данными и выполнением запросов.
